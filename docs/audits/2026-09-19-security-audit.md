## 1. Posture summary

The application's trust model is unusually explicit and mostly holds up under source review: the Data API roles hold no privileges on `public`, every read and write goes through a service-role client behind application-level `user_id` predicates, the answer model has no tools and its output is rendered by a hand-rolled text-only renderer, quota accounting is atomic and fail-closed, logs are whitelist-redacted, CI runs on pull requests with no secrets, and the SQL layer pins `SECURITY INVOKER` and `search_path` on every function. Of 30 coverage units, 14 closed with no candidate.

Zero findings were **confirmed**. 10 source-grounded leads remain **needs_validation**: each names a real code path whose exploitability turns on a deployment or provider fact (Vercel edge behaviour, hosted Supabase Auth settings, browser defaults) that source cannot fix and that this run was not permitted to observe. The two leads worth the owner's first attention are the Supabase session cookie issued without `Secure` (fixable in three lines regardless of the open question) and the two quota-scope gaps that make per-subject spend limits weaker than the runbook assumes. 4 candidates were rejected by independent verification.

## 2. Confirmed findings

None. No candidate met the confirmed bar in a source-only run; see §3.

## 5. Hardening notes

Observations that do not cross a trust boundary today but would make a control independent of an assumption it currently rests on. None is a finding.

- **ci-workflows-supply-chain** — push-email-templates.ts's --check drift output reports only string lengths, not content.
- **ci-workflows-supply-chain** — deploy-wizard.sh's _strip_invisible strips zero-width/BOM/CR characters from pasted dashboard values before they are written to .env.prod or used as header values.
- **browser-csp-dom** — src/lib/citations.ts's isCitation() only checks typeof url === 'string' || null on restore, not an http(s) scheme — safe only because persist.ts's saveQuestion is the sole writer of questions.citations and always supplies a Citation[] already scheme-gated by citationUrl(). Adding the same /^https?:\/\//i check to isCitation would make the restore path independently safe.
- **browser-csp-dom** — Confirmed by grep: no service worker registration, no postMessage usage, and no localStorage/sessionStorage use exist under src/ outside tests.
- **dependency-install-provenance** — pnpm-lock.yaml has zero git+/tarball/github:-sourced dependencies; every one of its resolutions is registry-fetched with a committed integrity hash, and the single-importer workspace (pnpm-workspace.yaml declares no `packages:` field) rules out internal-workspace-name dependency confusion.
- **dependency-install-provenance** — The `overrides.undici: ^8.10.0` hoist in pnpm-workspace.yaml is fully effective: pnpm-lock.yaml resolves every consumer (including the whole @ai-sdk/* chain) to a single `undici@8.10.0`, with no stray `undici@7.x` transitive escaping the override.
- **dependency-install-provenance** — `allowBuilds` in pnpm-workspace.yaml is a real, pnpm-recognized default-deny allowlist (verified by reading pnpm 11.5.2's own bundled source), not a no-op — and all four allowlisted names correspond to packages actually resolved in the current lockfile, so it is not pre-authorizing a name absent from today's tree.
- **dependency-install-provenance** — @base-ui/react and @shadcn/react — the two scoped runtime dependencies flagged as shipping into the browser bundle — both carry package.json `repository`/`homepage`/`author` fields consistent with their claimed upstream projects (mui/base-ui and shadcn-ui/ui respectively); no namespace-confusion signal found.
- **ingestion-upstream-payloads** — pdf.ts and scripts/ingest.ts run pdftotext/pdfimages/unzip (native, historically CVE-prone binaries) directly against bytes fetched from external official sites, inside the same recrawl.yml job that holds SUPABASE_SERVICE_ROLE_KEY and VOYAGE_API_KEY in its environment (recrawl.yml:56-62). No process isolation separates untrusted-content parsing from secret-bearing steps; a memory-safety bug in poppler-utils or unzip triggered by a malicious upstream payload would execute with those secrets in env. Worth isolating (run extraction in a step/job with no secret env, or a minimal-privilege container).
- **ingestion-upstream-payloads** — ccss-faq.ts/ccss-prescripcion.ts's absoluteUrl() accepts any URL scheme when inlining upstream href/src into chunk text; adding an http/https allowlist at the point of inlining would be cheap defense-in-depth.
- **ingestion-upstream-payloads** — source.sha256 and the layout drift notices are warn-only by explicit design — a standing hardening opportunity (e.g. fail closed on carriesFigures documents whose hash changed) rather than a new finding.
- **cookie-csrf-state-changes** — Ordinary CSRF: no dedicated anti-CSRF token or Origin/Referer/Sec-Fetch-Site check exists on POST /api/account/delete, DELETE /api/history/[id], or the cookie-identity path of POST /api/ask, but @supabase/ssr's unmodified default `sameSite: 'lax'` (verified via node_modules, no override anywhere in src/) already blocks cross-site top-level form POST navigation and all cross-site subresource fetch/XHR credentialed requests in SameSite-compliant browsers (the modern baseline since ~2020); DELETE is additionally unreachable via a plain HTML <form>. Recommend an explicit Origin/Sec-Fetch-Site check as defense-in-depth only against future config drift (e.g. someone later adding `cookieOptions.sameSite: 'none'` for an unrelated reason) -- not because the current control is presently ineffective.
- **cookie-csrf-state-changes** — The stateless `getClaims` verification tail (session/token remains valid until natural jwt_expiry even after sign-out) is the same mechanism as the already-accepted #358 deleted-account tail; not re-reported, but noted in the cookie-csrf-state-changes unit because it compounds the impact window of the missing-Secure-cookie candidate.
- **account-delete-lifecycle** — src/app/api/history/route.ts and [id]/route.ts swallow every query/delete error into a generic catch with no console.error/describeError call (unlike persist.ts and rate-limit.ts). Not a tenant-isolation defect, but a failing history read/delete leaves zero operational trace.
- **account-delete-lifecycle** — core_schema.sql's initial GRANT ALL to anon/authenticated (745-747) is superseded by least_privilege.sql; verified current-state privileges via the pgTAP guard rather than the historical migration.
- **account-delete-lifecycle** — rate_limits rows keyed by user:${uid} are not cleaned up by the auth.users CASCADE (no FK) — a deleted authenticated user's quota-count row lingers until the 2-day retention sweep. No unauthorized reader (opaque count keyed by a UUID, visible only to service_role). Hardening only.
- **ask-wildcard** — route.ts:930's onError door passed to createUIMessageStream is effectively unreachable: execute's own try/catch/finally never lets its promise reject and writer.write() failures are swallowed by the SDK's safeEnqueue. Defensive, not a vulnerability.
- **ask-wildcard** — If that onError door were ever reached, telemetry.emit() is idempotent and fires on the first call, so a fact recorded only via that later path would never reach the emitted event — a latent observability gap worth a regression test if execute()'s error handling is refactored.
- **ask-wildcard** — The query-embedding cache in src/lib/ingestion/embedder.ts (500-entry FIFO, module-wide) is a shared resource, but eviction cost is 1:1 with insertions — no superlinear growth.
- **ask-wildcard** — The step catalogue fixes 2-4 sentences per family, so STEPS_RERANK=max cannot be pushed higher by attacker-chosen text; worth a bound check if a future family entry grows.
- **ask-wildcard** — rate_limit_increment is a single INSERT ... ON CONFLICT statement, so concurrent asks for one subject cannot race past the daily cap.
- **ask-prompt-injection** — condense.ts's buildCondensePrompt and prompt.ts's buildUserPrompt interpolate client-supplied text into label-delimited templates ('Persona:'/'Asistente:', 'Pregunta:'/'Documentos oficiales') with no fencing. A crafted turn or question can forge a fake block; traced end to end the forged content only feeds that same requester's own condensation, retrieval and answer — not a cross-principal boundary today. Recommend fencing/quoting each interpolated field as defense-in-depth before any future feature shares threads across principals.
- **ask-prompt-injection** — invariant.ts checks only marker resolvability, not per-claim groundedness (documented as eval-time-only). Worth a source comment cross-referencing the confusion mode: a validly-numbered citation whose claim substance came from injected content in the requester's own prompt.
- **ask-prompt-injection** — Ingestion's SHA-256 mismatch is a warning, not a block; combined with formatChunks' unmarked trust of retrieved chunk content as 'documentos oficiales', a stale or altered official document gets no additional scrutiny before being cited. See uncovered.

Confirmed from the installed dependency.

- **ask-identity-tier** — The accepted ≤1h deleted-account token tail (#358) applies identically to user.ts's cookieUserId and history.ts's sessionUserId — not re-reported.
- **ask-identity-tier** — Magic links are deliberately redeemable from a different browser/device than the one that requested them (the 6-digit-code path exists for #85's in-app-browser case) — an intentional UX choice common to magic-link auth, not a control gap.

Effect would be a fairness/availability footgun, not a bypass.

- **search-chunks-sql** — Every vector argument reaching search_chunks is a JSON.stringify of a provider response already validated as finite numbers of the pinned width.
- **search-chunks-sql** — least_privilege.test.sql asserts both the negative (anon/authenticated/PUBLIC have nothing) and a positive control per RPC and per table, which catches an overzealous future revoke as well as an under-strict one.
- **csp-report-intake** — csp-report route intentionally carries no per-IP/global rate limit; per-request cost is bounded, so a flood only grows console log volume — a coarse limiter is worth adding only if Vercel log-ingestion volume becomes an observed problem.
- **csp-report-intake** — csp-report's readCappedBody has no read/wall-clock deadline; a slow-drip POST body could hold a function instance open up to Vercel's platform default max duration — bounded by an upstream, deployment-only control.
