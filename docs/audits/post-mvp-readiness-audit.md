## 1. Executive summary

**Verdict: the engineering core is genuinely strong and close to trustworthy — but the MVP is not finished, and the highest-risk gaps are exactly at the seam the product stakes its identity on: the moment an answer meets its evidence.**

Tramitico's retrieval and evaluation machinery is real and verified: a 25-question eval with a blocking canary passes 25/25 through the production retrieval path (independently re-run during this audit against the live 793-chunk corpus), the groundedness gate has a pinned judge with a majority rule, seven ADRs document decisions with data — including negative results — and the live answer observed in this audit was grounded, honest about its gaps, and correctly cited. That is rarer than it sounds, and it is the product's spine.

Against that spine, the audit found a cluster of verified defects concentrated on citation fidelity and real-user experience:

- **Saved history never renders its citations** — a key-name mismatch in `qa-view.tsx` empties every persisted citation list, and even the fallback rendering drops the hyperlink. The product's one differentiator silently vanishes on the returning-user surface. (Found independently by two audit tracks; verified.)
- **Raw `[n]` chunk markers and RAG jargon ("según los fragmentos") leak into user-visible prose**, live and persisted — internal plumbing showing through the notarial finish.
- **Citation links land on the document, not the artículo** — Ley IVA Art. 7 and Art. 8 share an identical URL — so "verify it yourself" costs the user a search through a full legal text.
- **The UI looks multi-turn but the backend is single-turn**: follow-up questions silently lose all context. Undocumented anywhere.
- **The MVP done bar is unmet**: not deployed ([#29](https://github.com/rjwrld/tramitico/issues/29) open), README is create-next-app boilerplate, `how-it-was-built.md` does not exist ([#28](https://github.com/rjwrld/tramitico/issues/28) open). "Post-MVP readiness" is being assessed for a product that has not yet shipped its MVP.
- **`effective_date` is null for all 14 corpus documents** — SPEC §3's freshness promise is half-implemented, and nothing surfaces source dates to users of a product whose subject matter changes by annual decree.

None of these are architectural; all are shallow relative to the quality of the foundation. The strategic risk is different: the temptation to expand surfaces (MCP, BYOK, mobile features) before the citation-fidelity core is airtight on the one surface that exists. The recommended direction (§21) is: **finish the MVP done bar, repair the evidence seam end-to-end (live → persisted → linked), then expand along the already-planned MCP path — which the architecture is one refactor away from supporting.**

## 2. Methodology and limitations

**What was done:**

- Read the full contract set (SPEC, DESIGN, PRODUCT, BRIEF, CONTEXT.md, all 7 ADRs, eval/README, docs/agents/*) before evaluating code.
- Independently re-ran verification: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — plus the DB-dependent integration suites and the 25-question retrieval hit-rate eval against the live local Supabase (which happened to be running with a fully ingested 793-chunk voyage-3 corpus).
- Live browser inspection of the dev server: empty state, streaming, completed answer, light/dark themes, login, DOM/accessibility-tree inspection, at 1440×900, 1280×800, 375×812, and 320×568. One real question was asked end-to-end (the ADR-0003 canary) to observe streaming, citation arrival, and answer quality against production keys.
- Four parallel deep-dive investigations: backend reliability/security/privacy; frontend UX/accessibility/design-contract compliance; testing/eval/ingestion/CI; and AI-access feasibility research against current provider documentation.
- Database inspection (read-only SQL) of documents, chunks, questions, and rate-limit state.
- GitHub issue state review (`gh`).

**Limitations:**

- **The groundedness eval was not re-run** (it spends real Anthropic tokens); its 25/25 result is taken from `eval/README.md` with its own documented caveat (7 weak-flagged cases auto-passed in the 2026-08-06 run — see F-26).
- **No screen-reader testing** was performed (VoiceOver/NVDA behavior of the `role="log"` streaming region is an explicit Unknown, U-3).
- **No production deployment exists**, so production latency, TTFT, LCP/INP/CLS, and cold-start behavior are unmeasured; §8 provides a measurement plan instead of numbers.
- 768×1024 and landscape-mobile viewports, 200% text zoom, and virtual-keyboard behavior were not exercised live; code-level signals are reported instead (rem-based type, `dvh` usage) with the residue listed as unknowns.
- Signed-in flows (history sidebar, deletion) were audited by code and jsdom/integration tests, not driven live (no test account was created, to avoid mutating local auth state).
- Five previously-observed integration failures with env-present-but-dead DB were not reproduced (the local DB was alive); the _mechanism_ (presence-only `hasDb` check) was verified instead, and a third outcome — env present, live DB, wrong embeddings provider → 10 hard failures — was reproduced directly.

Where a finding rests on an agent's file:line citation that I did not independently re-open, confidence is marked accordingly. Environment failures are kept separate from product findings throughout, per the engagement's rule.

## 3. Product and architecture map

**Product in one sentence:** anonymous or signed-in users ask a CR tax/trámite question in Spanish; the system retrieves from 14 official documents (793 article-level chunks), streams a cited answer with sello chips linking to official sources, and signed-in users get history (50/day vs 10/day anonymous).

**The ask flow as built** (`src/app/api/ask/route.ts`):

```
middleware (session refresh, JWT verify #1)
  → parse/validate body (400 before any cost; max 1,000 chars)
  → getUserId (JWT verify #2 — duplicated work)
  → rate limit (atomic INSERT..ON CONFLICT increment; fail-closed 503 vs 429)
  → retrieve: embed query (Voyage, paced/retried, no timeout)
       → search_chunks RPC (hybrid RRF: vector leg + lexical AND→OR fallback,
         coverage-scaled fusion, per-leg ranks; ADRs 0005/0006)
  → isWeak? (no chunk corroborated by both legs) → deterministic honest fallback, no model call
  → rerank (Voyage rerank-2.5-lite, pool 40 → top 8, 3s timeout, fail-open to fused order)
  → streamText (Claude Sonnet 5 default, env-swappable; system prompt = 7 prioritized guardrails)
       → onChunk: citation tracker parses [n] markers → cumulative data-citations snapshots (ADR 0004)
       → onFinish: persist question+answer+citations (signed-in only; failures logged, swallowed)
```

**Module inventory** (using the deep-module vocabulary; full analysis §11):

| Module                                               | Interface                                                        | Depth                                                                 | Adapters at the seam                                  |
| ---------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------- |

## 4. Verified strengths

These are load-bearing and should be preserved (see also §24):

1. **The eval harness is real, layered, and re-runnable.** Retrieval quality (hit-rate ≥92% gate, blocking canary) is asserted separately from generation quality (groundedness ≥90%, pinned judge, temperature 0, majority re-judge) — exactly the separation §10's scope asks about. I re-ran the hit-rate eval during this audit: **25/25 through the production path, 17s wall-clock** against the live corpus. The dataset itself is shape-tested (`dataset.test.ts`: count, canary presence, doc_keys exist in manifest) so it cannot silently rot.
2. **ADR discipline is exceptional for any team size, let alone solo.** Seven ADRs with measured data, recorded negative results (input_type hints hurt → rejected on evidence), amendments when reality disagreed (ADR 0002's chunker amendment; ADR 0003's canary transfer and resolution), and honest numbering archaeology. This is the portfolio's strongest artifact and it is currently invisible from the README (F-33).
3. **The weak-retrieval path is a genuine responsible-AI mechanism, not theater.** `isWeak` → deterministic canned honest answer, zero model calls, zero citations, agency links (`route.ts:153`, `prompt.ts:18-23`) — simultaneously a hallucination guard and a cost control, and tested (`route.test.ts` asserts the model is never invoked).
4. **Rerank can never fail the ask.** Timeout 3s, every failure mode → fused order, seven dedicated tests (`rerank.ts`, `rerank.test.ts`). This is the fail-open pattern the embedding path should copy (F-02).
5. **Rate limiting is race-free by construction** — a single `INSERT ... ON CONFLICT` statement, not check-then-write — and fail-closed with a distinct 503-vs-429 contract, both branches tested.
6. **RLS is proven, not assumed.** Cross-user integration tests assert user B cannot delete user A's rows; `chunks`/`documents`/`rate_limits` are default-deny (RLS enabled, no policies — service-role only). Service-role key demonstrably cannot reach the browser bundle (all client-tree imports of server modules are `import type`).
7. **Citation URL hardening**: scheme-allowlisted (`/^https?:\/\//i` → else non-link sello), `target="_blank" rel="noopener noreferrer"`, answer rendered as plain text (no `dangerouslySetInnerHTML`, no markdown HTML injection surface).
8. **Ingestion is atomic and fail-loud.** `replace_chunks` RPC delete+insert in one transaction with a rollback-proving integration test; SINALEVI fetcher throws on shape drift instead of guessing; TLS verification kept on via a vendored intermediate rather than disabled; hacienda WAF handled with real Playwright fetching.
9. **The chunker was hardened against observed corpus pathology, not hypotheticals** — fragment rejoin and inline-heading splits trace to real Ley IVA markup failures documented in ADR 0002's amendment, with tests named after the actual bugs.
10. **The design system is implemented with unusual fidelity.** The sello matches DESIGN §5 to the pixel (anatomy, double rule, stamp-settle 180ms with a tested reduced-motion escape); red discipline holds under grep (zero hardcoded reds); `dvh` used correctly everywhere; light and dark are genuinely independently tuned (verified visually); rate-limit copy names the reset time and nudges sign-in without scolding, exactly per DESIGN §9.
11. **Privacy defaults are right.** Anonymous questions are never persisted; rate-limit subjects are salted-hash, not raw IPs; per-question deletion exists via RLS-scoped browser calls.
12. **The e2e configs encode a real cost philosophy**: default config pins server Supabase env empty so the fail-closed path is deterministic; the opt-in local config drives a genuine 429 with `RATE_LIMIT_ANON=1`, stub embeddings, and an empty Anthropic key — e2e that can never accidentally spend money.

## 6. Product and UX

**First-time comprehension (weak).** The empty state is beautiful but assumes the visitor already knows what Tramitico is. Nothing communicates: answers come from official documents; every answer is cited to an artículo; the corpus covers Hacienda + CCSS (and _not_ MTSS/labor law); it isn't advice. The disclaimer first appears _after_ the first answer — the one moment it matters most is before the first question (F-27). The positioning line in PRODUCT.md ("the only place where the answer arrives with the exact artículo that backs it") is exactly the sentence the empty state is missing, in quieter words.

**Time-to-first-question.** Desktop: excellent — seed prompt click → streaming within a few seconds (observed). Mobile: poor — the composer is below 3–4 screens of seed chips (F-07), and a user with their _own_ question (the common case per PRODUCT.md — "they arrive with a specific dreaded question") must scroll past all ten before finding the input.

**Seed prompts (G-12).** Ten equal pills is a spec-compliant implementation of "top-10 pain questions as one-click prompts" that has outgrown its presentation. There's no hierarchy (the IVA-export and CCSS questions are far more common), no category grouping (Hacienda vs CCSS vs facturación), and at mobile widths the list _is_ the landing page. Options worth testing rather than assuming: 3–4 headliners + disclosure; category clusters; rotation. Evidence to gather: which seeds get clicked (needs the minimal analytics decision, §15).

**The citation trust chain — the product's spine — currently has three broken links:**

1. Live prose → sello mapping is opaque (`[6][8]` markers vs three unlabeled chips; F-03).
2. Sello → source lands on the document, not the artículo (F-19).
3. Persisted answer → citations don't render at all (F-01).

A user who tries to _verify_ — the behavior the whole product exists to enable — hits friction at every hop. This cluster is the audit's central product finding: fixing it end-to-end (marker mapping, artículo-level links where possible, history fidelity) is worth more than any new feature.

**States.** Present and good: empty, pre-first-token ("Consultando los documentos oficiales…"), streaming, completion + disclaimer, weak-retrieval honest fallback, differentiated errors with Spanish copy (400/429/502/503), rate-limit message that names the reset and nudges sign-in. Missing: stop, retry, copy, new-question reset, history freshness (F-09, F-20). Mid-stream provider failure is an unknown-behavior state (F-22/U-2).

**Follow-ups (F-05, G-2).** The single-turn engine behind a multi-turn surface is the audit's sharpest product-honesty issue. BRIEF §9 explicitly asked "is chat the right UI, or is a searchable Q&A format more honest?" — the shipped compromise (chat chrome, Q&A engine) is the one combination that answers that question wrong on both sides. Either commitment is fine; the silent middle is not.

**Authentication motivation (good).** The login page says exactly why to sign in (history + 50/day). The 429 nudge reinforces it. Friction is low (magic link + GitHub).

**Returning users.** History exists desktop-only (F-06), doesn't refresh live (F-20), renders answers without their citations (F-01) and with the leaked markers (F-03). The returning-user experience is the least-finished surface of the product — notable because retention of a small peer group is the stated adoption path.

**Effective dates / freshness (F-18).** No user-visible dates anywhere: not on sellos, not on answers, not on a corpus page. For tax law — where "vigente" is the operative question — surfacing `effective_date`/`fetched_at` ("Consultado el 6 ago 2026") is cheap trust the product already half-collects.

**On the §-scope question list** (stop/retry/copy/copy-citation/follow-ups/new-question/source-preview/report-answer/corpus-coverage/remaining-quota/dates): assessed individually in §15's opportunity map rather than assumed buildable — with stop+retry (F-09) and dates (F-18) as the two with immediate evidence behind them.

## 7. Responsive experience and accessibility

**Viewports exercised live:** 1440×900, 1280×800, 375×812, 320×568 (light+dark). 768×1024 and landscape were not exercised (limitation §2); code signals (flex wrap, `max-w-[44rem]`, rem type) suggest no structural risk there, low confidence.

**Verified responsive findings:** composer below fold on phones (F-07); no history below `md` (F-06); no safe-area inset (F-28); placeholder truncation at 320 (cosmetic); no horizontal overflow at any tested width (good); `h-dvh`/`min-h-dvh` used correctly with zero `vh` remnants (good — the classic mobile chrome bug is pre-avoided). Virtual-keyboard behavior and 200% text zoom were not exercised; rem-based typography and `dvh` are the right preconditions, so both go to the verification plan rather than findings.

**Touch targets.** Nothing reaches 44×44: default buttons 32px, sello ≈25px, icon-xs exactly 24px. Under WCAG 2.2 AA (2.5.8, 24px minimum) everything passes with no margin; under the 44px best-practice bar nothing does. Note the contract mismatch: PRODUCT.md commits to WCAG **2.1** AA (no target-size criterion) while this audit was asked for **2.2** — worth updating PRODUCT.md to 2.2 deliberately (the delta is small: target size 2.5.8 passes today; focus-appearance and dragging don't apply meaningfully).

**Accessibility summary** (details in F-08, F-30, F-31, F-32, F-21, F-34):

- **Streaming**: the engagement asked directly — _continuous announcement, completion summary, or another pattern?_ Recommendation: **completion summary + status region**. Continuous token announcement of legal prose is unusable; the pattern is (1) `role="status"` on the "Consultando…" indicator, (2) `aria-busy` on the answer container during streaming, (3) one polite completion announcement including the citation count, (4) answer prose readable in browse mode, never force-announced. The vendored `role="log"` region needs to be either tamed (it may announce every appended node) or replaced — decide after one VoiceOver session (U-3).
- **Keyboard**: all controls are reachable (native buttons/links/forms — a real benefit of the no-custom-widget restraint); focus-visible styles present including on sellos; the two view-branch transitions drop focus (F-30); streaming disables controls silently (no explanation for why Enviar and all ten seed pills left the tab order).
- **Semantics**: landmarks good (`header`/`main`/`form`/`nav aria-label="Historial"`); headings absent post-ask (F-31); sello links have accessible names matching visible labels (tested in `sello.test.tsx`) and correct external-link protection; the sello row is a labeled group ("Fuentes"). External-link _indication_ (that it opens a new tab) is absent — acceptable under the "chip is the link" design, worth an `aria-label` suffix ("se abre en ventana nueva") at XS cost.
- **Spanish language behavior**: `lang="es"` is right for the shipped chrome; the handful of English labels inside it get Spanish-phoneme voicing (F-32). Note the chrome-language contract conflict is a doc-level issue (G-1), not a code bug.
- **Contrast**: token values match DESIGN §2's documented AA floors (ink 14.9:1, sello 6.3:1, muted ≥4.6:1); dark theme reads correctly in live inspection. Not re-measured instrumentally — DESIGN's own numbers are taken at face value; a contrast pass belongs in the verification plan with axe or similar.
- **Destructive confirmation**: history delete has a proper inline confirm with explicit verbs — a strength worth keeping exactly as is.

## 8. Visual design, motion, and performance

**Does "Notaría moderna" hold up?** Yes — this is the audit's clearest positive design judgment. Against the §-scope criteria: trust (the sello reads as provenance, not decoration), clarity (one accent, policed — grep-verified), source verification (the chip _is_ the link — right idea, undermined only by F-19's document-level URLs), long-form reading (68ch, 1.7 line-height, `text-pretty` — correct), mobile (structure survives; the failures are layout priorities, not identity), emotional reassurance (the empty-state headline is an invitation, the error copy has no apology theater), cultural relevance (trami·tico, usted, no flags), memorability and portfolio distinction (a chat product that looks like _paper and ink_ instead of gradients-and-sparkles is genuinely differentiated; the anti-references list in PRODUCT.md is being honored). **Recommendation: no direction change — refinements only.** The deviations found are small and enumerable (F-36/37/38, tinted destructive, tracking) — the kind of drift a token-audit pass fixes in an afternoon.

## 10. Retrieval and groundedness

**What's verified working:** article-level chunk identity with context headers (ADR 0002 + amendment); hybrid RRF with the AND→OR conditional fallback (ADR 0005); coverage-scaled fallback fusion with per-leg ranks (ADR 0006); rerank lifting 19/25 → 25/25 with the canary as a named blocking case (ADR 0003 amendment — **independently re-verified in this audit: 25/25, live corpus**); structural weak-retrieval detection (`isWeak` = no chunk in both legs); citation dedup in order of first use, delta-buffer-safe; prompt constraints that measurably produce honest gap acknowledgment (observed live: the answer explicitly said what the fragments _don't_ cover and pointed to Hacienda).

**Where the audit pushes:**

- **Corroboration as the sole weakness signal (G-3).** `isWeak` fires only when _no_ returned chunk appears in both legs. Under ADR 0006's coverage scaling, fallback-branch queries are mostly vector-carried by design — so a question whose true source only the vector leg can reach sits structurally closer to "weak" even when retrieval is right, and conversely a generic question can be "corroborated" by vocabulary overlap alone. The eval says every current legitimate question clears it — but n=25, and the boundary's behavior on paraphrases and out-of-corpus questions is unasserted (only one weak-path case exists in the e2e stubs; no eval case asserts a _should-be-weak_ question actually trips it). A "should-refuse" eval slice (questions the corpus genuinely can't answer — e.g. an MTSS aguinaldo question, a Renta Global Dual question) would test the refusal boundary from both sides.
- **Dataset language vs user language (G-4).** The canary exists precisely because users don't speak corpus vocabulary — one blocking case of 25. Several dataset questions read corpus-flavored. The cheapest fix is the already-planned post-launch peer-question collection (BRIEF: explicitly deferred) — the audit's addition: **log real questions (hashed user, raw question, retrieval ranks) from day one** so the dataset's second generation is harvested, not authored. This is also the only way to measure the weak-trigger false-positive rate on real traffic.
- **25/25 saturation.** Both the hit-rate and groundedness gates are at ceiling; a gate at ceiling can only detect catastrophic regressions and can no longer discriminate improvements (Sonnet vs Haiku already tie at n=25). Fine for MVP; the growth path is dataset expansion (peer questions), not threshold tuning.
- **Judge caveats (G-9).** The judge is binary supported/unsupported at answer granularity — a numerically-wrong-but-cited figure inside an otherwise supported answer can pass. Numeric-claim spot-checks (assert the tramo figures and BMC amounts in answers match the decree text) would be a cheap, high-value eval extension for exactly the claims where SPEC says aggregators disagree. Also: the 2026-08-06 measured run auto-passed 7/25 weak cases (F-26) — re-measure clean before quoting.
- **Live vs persisted evidence fidelity:** structurally identical server-side (same tracker output persists) — and then the history UI drops it all (F-01). Marker-bearing prose persists as-is (F-03), so history fidelity repairs must handle both.
- **Corpus blind-spot communication:** the MTSS gap is encoded in the prompt (rule 4 states the Labor-Code fact) — good. But coverage limits are invisible in the UI (F-27): a user cannot distinguish "the corpus doesn't include this" from "no hay base oficial", which reads as "the law is silent" — a materially different claim. The weak-retrieval copy could name the corpus's actual scope in one clause.

## 11. Architecture

**The route is thin orchestration over genuinely deep modules** — eight concerns in sequence, each a one-line delegation; the complexity lives one level down where it's testable. This is the right shape and does not need decomposition on its own merits (agreeing with the backend investigation against the "excessive responsibility" hypothesis in the engagement scope).

**Real seams vs hypothetical, per the two-adapter rule:**

- **Embedder: real** (3 adapters — stub/voyage/openai — behind one interface; the stub adapter is what makes tests and keyless dev work, so the seam earns its keep daily).
- **Rerank: half-real** (voyage + identity-fallback; inline branching, not an interface — correct at current scale; lift only if a second reranker appears).
- **Answer model: not a seam** (env-var model _id_ within one provider; `getAnswerModel`'s construction-in-module is fine — the module _is_ the construction). A second provider (BYOK-Anthropic-vs-OpenAI, §16) would make it one; do not pre-build the hierarchy.
- **Delivery surface: not yet a seam** (web only). The MCP server is the event that creates it.
- **Retrieval → generation boundary: the latent seam that matters.** `retrieve()` already returns almost exactly the report-scoped `EvidencePackage` (chunks + identity + citations + weak signal + per-leg ranks); what's missing for a second consumer is source metadata (URL, effective/fetch dates — F-18 again) and a stable citation identity (`citationIdentity()` exists). §20 evaluates the extraction options.

**Confirmed smells (all with findings attached):** duplicated citation formatting between live and persisted paths — and the duplicate is _wrong_ (F-01), the textbook cost of a shallow lookalike instead of reusing the deep component; domain values as `unknown` at exactly one boundary (`citations as unknown as Json`) with the mirror guard (`parseCitations`) built but never wired (the enabler of F-01); hidden environment coupling in `clientIp` (F-23) and in the four-knob CI gating (F-16); dead code (`ui/message.tsx`, `ui/bubble.tsx`, F-39). **Not found:** premature abstractions (the codebase is notably restrained), shallow pass-through modules (the thin ones — model.ts, persist.ts — are thin for defensible reasons), provider construction buried inside business behavior.

**Locality/leverage assessment:** the ask contract (`contract.ts`), service-client policy (`service.ts` per CONTEXT.md), and citation identity (`retrieval.ts`) each live in exactly one place with multiple consumers — good leverage. The one leverage failure is sello rendering (two implementations, one broken — F-01).

## 16. AI access, BYOK, and subscription feasibility

Full research memo with per-claim citations was produced during this audit; the load-bearing conclusions (all retrieved 2026-08-07):

**The subscription boundary is hard, explicit, and enforced.** Anthropic: "Anthropic does not permit third-party developers to offer Claude.ai login or to route requests through Free, Pro, or Max plan credentials on behalf of their users" ([Claude Code legal & compliance](https://code.claude.com/docs/en/legal-and-compliance); corroborated by the [Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/overview)), with real enforcement actions against subscription-arbitrage tools in early 2026. OpenAI: ChatGPT and API billing are formally separate ([billing help](https://help.openai.com/en/articles/9039756-managing-billing-settings-on-chatgpt-web-and-platform)); the new "Sign in with ChatGPT" (beta, 2026-08) is an **identity/SSO product** delivering name/email/avatar — it does not provision model access. **Therefore: no compliant mechanism exists for Tramitico's standalone website to spend a user's consumer subscription.** The only place a user's subscription pays for Tramitico-grounded answers is _inside the provider's own product_, with the provider's model calling Tramitico's MCP tools.

**Pricing facts that change a standing assumption:** Claude Sonnet 5 is at intro pricing ($2/$10 per MTok) **through 2026-08-31 only**, then $3/$15; Haiku 4.5 is $1/$5. The eval README's "~5× cheaper per output token" for Haiku is stale — the sticker ratio is 2–3×, _and_ Sonnet 5's newer tokenizer emits ~30% more tokens for the same Spanish text, so the honest comparison requires `count_tokens` on real Tramitico prompts, not a price ratio ([pricing docs](https://platform.claude.com/docs/en/about-claude/pricing)). Voyage's free allowance is one-time 200M tokens (not monthly, third-party corroborated — re-verify under MongoDB's billing before relying on it); either way it is immaterial at this scale.

**Cost per grounded answer (order of magnitude, standard pricing):** ~3–5K input + ~500 output tokens ≈ **$0.9–2¢ (Sonnet 5 standard) vs ~$0.3–0.7¢ (Haiku 4.5)** — call it roughly 1–2 US cents vs half a cent. At 50 users × 5 questions/day: ~$75–150/mo Sonnet vs ~$25–50/mo Haiku, plus negligible Voyage. Product-funded inference is sustainable at portfolio-and-peers scale under either model; the rate limiter is what keeps it that way (and its fail-closed design is correctly aligned with this).

**BYOK:** session-only in-memory proxying of a user's own _API key_ is the only variant worth ever considering (verdict: defer until a real user hits the authed limit); encrypted persisted custody is rejected (a solo-maintained portfolio app custodying strangers' live secrets is a bad trade at any plausible demand); direct-browser generation is rejected on architecture fit (retrieval/rerank/citations are server-side; shipping chunks to an untrusted client to save nothing). Note the unresolved ToS gap (U-9): neither provider's terms explicitly address third parties custodying end-users' own API keys — silence is not permission.

**Remote MCP (the interesting one):** Claude custom connectors work on **every plan** (Free capped at one) by URL; authless (`none`) mode is supported and fits a read-only public-tax-information server; Directory listing — but only listing — requires a Team/Enterprise org ([connectors docs](https://claude.com/docs/connectors/custom/remote-mcp), [submission](https://claude.com/docs/connectors/building/submission)). Current MCP spec (2025-11-25) prefers CIMD over DCR, mandates PKCE S256 and audience-bound tokens, forbids token passthrough. ChatGPT's Apps SDK is the same shape (MCP + widget layer) with a younger review pipeline; end-user plan-tier availability could not be confirmed (U-10). Tool results render as text the host model quotes — **citation presentation inside hosts is prose-level, not sello-level**, so the evidence payload must carry its own identity (doc, artículo, URL, dates) in a shape the host model will reproduce: this is precisely the EvidencePackage argument (§20).

**Recommended access strategy per segment:** anonymous web → product-funded, 10/day, fail-closed (unchanged); signed-in web → product-funded 50/day (unchanged; re-baseline Sonnet-vs-Haiku before the price cliff); advanced technical users → nothing new now (session-BYOK deferred until demanded); Claude subscribers → **the unlisted custom connector, built against the shared evidence engine** (their plan pays for inference; Tramitico pays only retrieval); ChatGPT subscribers → deferred until the Claude connector proves value.

Against: the same weeks could fund mobile history + follow-up context + peer eval round — direct user value. Consequences if wrong: an MCP server no one connects to, while web UX debt sits. Open questions: does anyone in the peer group actually use Claude/ChatGPT with connectors? Cheapest validation: ask the peer group (n≈10) one question. Owner: RJ. Blocks the §22 "Later" ordering only.

**G-8 · "Sonnet by default; Haiku is the ~5× cheaper alternative."**
Why wrong: the 5× figure is stale (§16: 2–3× sticker, minus tokenizer effects); the intro-price cliff (2026-08-31) changes Sonnet's cost 50% upward next month; both models tie 25/25 at n=25 so the gate cannot justify the premium. **G-9 · "A binary answer-level judge at ≥90% is the right groundedness gate."**
Why wrong: binary at answer granularity passes answers whose _numeric_ claims are wrong-but-cited; the judge is a previous-generation model (ADR 0007 accepts this); the gate saturates. Evidence for: majority rule absorbs flake; pinned judge keeps comparisons honest; ADR 0007's own consequences section anticipates revisiting. Against: the domain's highest-stakes claims are numbers (tramos, BMC, 13%); no claim-level check exists. Consequences: the gate's blind spot is exactly where user harm concentrates. Cheapest validation: 5 numeric-claim assertions (regex/string checks against decree figures in answers to the tramos/BMC/IVA-rate questions) — deterministic, no judge needed. Owner: RJ. Not blocking; high value per effort.

Cheapest validation: seed-click logging (§15) for two weeks → keep the top 3–4 visible, fold the rest. Owner: RJ. Not blocking.

## 20. Architecture alternatives

The engagement's proposed concepts (EvidenceEngine / AnswerGenerator / ProviderCredential / DeliverySurface) mapped against what exists:

**Already exists in substance:** EvidenceEngine ≈ `retrieve()` + `rerankChunks()` (returns chunks, citations, weak signal, per-leg ranks); AnswerGenerator ≈ `prompt.ts` + `model.ts` + the streaming block; citation identity ≈ `citationIdentity()`. **Missing from the EvidencePackage shape:** source URL + effective/fetch dates travel on `Citation` but not on chunks; coverage warnings are a boolean, not a statement; nothing packages these for a non-web consumer.

**Alternative A — status quo until MCP work starts.** Keep the thin route; do nothing structural. Cost: none now; the MCP server would then either duplicate retrieval orchestration or import route internals. Right choice _if_ MCP slips beyond ~a quarter.

**Alternative B — extract the evidence seam when (and because) the second consumer arrives.** One module: `question → EvidencePackage {chunks, citations w/ identity+URL+dates, weak, retrievalSignals}` — literally today's `retrieve`+`rerank` composed, plus F-18's dates. Web route and MCP server both consume it; the groundedness eval evaluates _it_ separately from generation (which §10 wants anyway); citation identity stays stable across web, history, and MCP because all three read the same package. Cost: S — it's a composition of existing deep modules, not new abstraction. This is the recommended path, _triggered by_ the MCP build, not before ("one adapter = hypothetical seam; two = real": the MCP server is adapter #2 of the delivery surface, and its existence is what makes the seam real).

**Alternative C — full provider abstraction now (AnswerGenerator interface + ProviderCredential hierarchy).** Rejected: exactly one generation provider exists and §15 rejects the second; a credential hierarchy for BYOK that's deferred is a hypothetical seam squared. The grill that kills it: name the second concrete adapter that would consume it this year — there isn't one (session-BYOK is deferred; MCP doesn't need it — the _host_ holds the model).

**Tension worth keeping open (not forcing):** whether ask orchestration (rate limit → evidence → generate → persist) should itself become a module when the MCP server needs a different policy mix (no rate limit table? host-enforced quotas? no persistence?). Two orchestrations over one EvidenceEngine is fine; don't pre-unify them — let the MCP server's real requirements decide whether shared orchestration is leverage or coupling.

## 21. Recommended strategic direction

**Finish, repair the evidence seam, then widen the funnel through MCP — in that order, with real-user telemetry started at deploy.**

1. **Finish the MVP** (#29 deploy + #28 docs, folding in security headers and the timing log). Everything in this audit is theoretical until a URL exists.
2. **Repair the citation trust chain end-to-end** (F-01/03/04/19-investigation/18): the product's differentiator must survive live streaming, persistence, revisit, and the click to the source. This is "post-MVP readiness" in one sentence.
3. **Make the real-user surface honest and reachable**: single-turn framing decision (D-2), mobile composer + history, streaming a11y pattern, stop/retry.
4. **Grow the eval with reality**: logging → peer questions → should-refuse slice → numeric-claim checks. The gates are at ceiling; only new data makes them meaningful again.
5. **Then the Claude MCP connector as the strategic expansion** — unlisted custom connector, authless read-only tools, built by extracting the EvidencePackage seam (Alternative B). It's the planned phase-2, the only compliant subscription-user path, the portfolio's "builds MCP servers" unlock, and the forcing function for the architecture's one worthwhile refactor.
6. **Explicitly not now**: BYOK in any form, ChatGPT app, additional providers, corpus expansion beyond freshness hygiene — each deferred/rejected with reasons in §15/§16.
