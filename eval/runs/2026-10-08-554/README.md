# Where the Tier 1 misses go missing, 2026-10-08 (#554)

#512's two final lanes stated 78 and 79 of 116 Tier 1 requirements. This record
splits the requirements **both** lanes missed by where they go missing:

1. **Not in the corpus.** No chunk in `public.chunks` carries it.
2. **In the corpus, not in the answer set.** A chunk carries it, but neither
   that lane's retrieval nor its rerank and pins put it in front of the model.
3. **In the answer set, dropped by the answer.** The model saw a chunk that
   carries it and didn't state it.

It is free: no provider call, no write. The inputs are the two lanes'
groundedness transcripts in `eval/runs/2026-10-08-final/lane{1,2}/`, whose rows
carry each answer set's chunks, plus read-only `SELECT`s on the shared local
stack. That stack holds the same 873-chunk corpus the lanes ran on, and every
chunk id the transcripts name is still there.

## How «carries the requirement» was decided

By hand, once per requirement, and recorded in
[`carriers.json`](carriers.json): a chunk id and a quote from its text for
every carrier. The quote must state the substance the requirement names, the
same bar the adequacy judge applies. A heading that only names the topic
doesn't count. The search was lexical: the requirement's key phrases in the two
answer sets, then `ilike` and regex `SELECT`s on `chunks`, plus the case's own
`expected` targets.

Where a requirement has two halves and the answers stated one, only the missing
half is tagged, and the note says which. Where they missed both halves, each
half is a part, and the row takes the most upstream cause among its parts:
fixing the answer alone wouldn't state it.

`pnpm tier1-miss-causes` does the rest mechanically. It finds the requirements
both lanes missed, takes each lane's cause from whether a carrier's chunk is in
that lane's answer set, and checks every quote against the chunk text wherever
a transcript row carries that chunk. 41 of the 42 carrier quotes are in some
row of the two lanes. The one that isn't was checked with the query below, on
the shared stack (`found`, `carries`: both true).

```sql
select q.id, c.id is not null as found,
  position(q.quote in regexp_replace(c.content, '\s+', ' ', 'g')) > 0 as carries
from (values
  ('a19f67fb-f30e-4f9d-bd28-747db533cedb', 'las fechas de pago van del día 5 al 9 de cada mes según la primera letra del primer apellido')
) as q(id, quote)
left join chunks c on c.id::text = q.id;
```

Five rows are flagged **uncertain**. Rows 12 and 15 rest on a weak carrier inside the set.
Rows 8 and 17 have a carrier that answers the requirement only in part. Row 26
has none that describes its step exactly, so it is cause 1 if that carrier
doesn't count. Taking every uncertain row the other way changes the counts by
at most five, and cause 2 stays the largest bucket.
